# SavariGo database

PostgreSQL 16 + Prisma 6. This document is the reference for the Phase 2 data
model: conventions, table catalogue, integrity rules and day-to-day workflow.

- Schema: [`prisma/schema.prisma`](../prisma/schema.prisma)
- Initial migration: [`prisma/migrations/20261109000100_init`](../prisma/migrations/20261109000100_init/migration.sql)
- ERD: [`erd.mmd`](./erd.mmd) (Mermaid)
- Seed data: [`prisma/seed.ts`](../prisma/seed.ts)

---

## 1. Conventions

| Concern | Rule |
| --- | --- |
| Primary keys | `uuid` generated by the database (`@default(uuid()) @db.Uuid`) |
| Table / column names | Prisma camelCase fields, mapped to `snake_case` tables via `@@map`; columns keep camelCase because Prisma quotes identifiers |
| Timestamps | `createdAt` defaults to `now()`; mutable rows carry `updatedAt @updatedAt` |
| Time zone | Prisma `DateTime` maps to `TIMESTAMP(3)` (no zone). Store UTC — the API and seed convert IST (`+05:30`) inputs to UTC before writing |
| Money | `Decimal(12,2)` for booking/payment amounts, `Decimal(10,2)` for rates, `INR` default. Never `Float` |
| Coordinates | `Decimal(9,6)` |
| Soft state | Enum columns (`status`, `verificationStatus`) instead of free-text |
| Delete behaviour | Money and booking history use `Restrict`; child detail rows use `Cascade`; optional references use `SetNull` |
| Indexes | Every foreign key used in filters, plus composite indexes for the query shapes the UI already performs (status + date, vehicle + date, owner) |

All tables also carry `createdAt` unless the row is an immutable join or log
record, in which case `createdAt` alone is present.

## 2. Table catalogue

### Identity and access

| Table | Purpose | Key relationships / indexes |
| --- | --- | --- |
| `users` | Account root for customers, drivers, vendors and staff | `email` unique, optional `phone` unique; index on `status` |
| `roles` | CUSTOMER, DRIVER, VENDOR, SUPPORT, ADMIN | `name` unique |
| `permissions` | Fine-grained capability keys (`booking:read`, `vehicle:write`, …) | `key` unique; index on `group` |
| `user_roles` | Many-to-many user↔role | Composite PK, index on `roleId` |
| `role_permissions` | Many-to-many role↔permission | Composite PK, index on `permissionId` |
| `refresh_tokens` | Rotating refresh tokens, stored as SHA-256 hashes | `tokenHash` unique; `replacedById` links each rotation; indexes `(userId, revokedAt)`, `expiresAt` |
| `verification_codes` | HMAC-hashed email/phone/password-reset codes | Index `(identifier, purpose, createdAt)`; `attempts` caps brute force; one-shot `consumedAt` |

### Profiles

| Table | Purpose | Notes |
| --- | --- | --- |
| `customer_profiles` | Rider name, DOB, licence, avatar, city, JSON preferences | One per user (`userId` unique) |
| `driver_profiles` | Driver licence, experience, languages, rates, availability | `licenceNumber` unique; index `(verificationStatus, isAvailable)` |

### Fleet

| Table | Purpose | Notes |
| --- | --- | --- |
| `vehicle_categories` | Bike / Scooter / Car grouping used across listings, filters and coupons | `slug` unique |
| `vehicle_locations` | Pickup hubs and drop points | `slug` unique; index `(city, isActive)` |
| `vehicles` | Inventory | `slug`, `registrationNumber` unique; `categoryId`, `ownerId`, `locationId`; indexes for category/status, hub/status, owner, popular/status and `(status, fromPrice)`; `fromPrice` is the denormalised lowest active day rate so price filtering and sorting happen in SQL |
| `vehicle_images` | Gallery | Index `(vehicleId, sortOrder)`; partial unique index enforces one primary image |
| `vehicle_availability` | Calendar rows that reserve or block time | `(vehicleId, startsAt, endsAt)`, `bookingId`, `(status, startsAt)`; GiST exclusion constraint prevents overlaps |
| `pricing` | Rate plans per vehicle | `(vehicleId, name, validFrom)` unique; index `(vehicleId, isActive)` |

### Bookings and money

| Table | Purpose | Notes |
| --- | --- | --- |
| `bookings` | Rental contract | `code` unique (e.g. `SVR8842`); customer, vehicle, pickup/drop hub, optional coupon and `driverId`; amount breakdown; lifecycle + payment status; index `(driverId, status)` for driver requests |
| `booking_items` | Immutable price lines (rental, helmet, delivery, driver, insurance) | `metadata` JSON for extras |
| `payments` | Gateway transaction record | `providerOrderId`, `providerPaymentId`, `idempotencyKey` all unique; `method` stays null until the gateway confirms checkout; **no card data** |
| `refunds` | Refund against a payment | `providerRefundId` unique; index `(paymentId, status)` |

### Promotion, feedback and operations

| Table | Purpose | Notes |
| --- | --- | --- |
| `coupons` | Discount definitions | `code` unique; percent/flat, caps, validity window, usage limits |
| `coupon_categories` | Restricts a coupon to vehicle categories | Composite PK |
| `reviews` | One review per completed booking | `bookingId` unique; rating CHECK 1–5; index `(vehicleId, isPublished)` |
| `notifications` | In-app / email / SMS / WhatsApp outbox | Index `(userId, readAt)` and `(status, createdAt)` |
| `addresses` | Saved rider addresses | Partial unique index enforces one default per user |
| `admin_settings` | Typed JSON configuration with audit trail | `key` unique |
| `audit_logs` | Who changed what | Index `(entityType, entityId)`, `(actorId, createdAt)`, `createdAt` |

## 3. Status models

```
Booking:  PENDING → CONFIRMED → ONGOING → COMPLETED
                 ↘ CANCELLED        ↘ NO_SHOW

Payment:  PENDING → PAID → REFUNDED | PARTIALLY_REFUNDED
                 ↘ FAILED

Refund:   PENDING → PROCESSING → COMPLETED | FAILED

Vehicle:  DRAFT → AVAILABLE ⇄ UNAVAILABLE | MAINTENANCE → RETIRED

Driver:   PENDING → VERIFIED | REJECTED → SUSPENDED
```

Amounts are stored as the final computed values (`rentalAmount`, `extrasAmount`,
`taxAmount`, `depositAmount`, `discountAmount`, `totalAmount`) rather than being
recalculated on read. That keeps invoices stable if pricing or tax rules change.

## 4. Integrity rules beyond Prisma

Prisma cannot express PostgreSQL exclusion constraints, partial indexes or
CHECK constraints, so the migration appends them after the generated DDL.

### 4.1 Booking conflict prevention

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "vehicle_availability"
  ADD CONSTRAINT "vehicle_availability_no_overlap"
  EXCLUDE USING gist (
    "vehicleId" WITH =,
    tsrange("startsAt", "endsAt", '[)') WITH &&
  )
  WHERE ("status" IN ('BLOCKED', 'BOOKED', 'MAINTENANCE'));
```

`btree_gist` lets a GiST index combine equality on `vehicleId` with overlap on
the time range. The `WHERE` clause means `AVAILABLE` rows (the default open
calendar) never conflict, while customer bookings, vendor blocks and maintenance
windows all reserve time. Two concurrent inserts for the same vehicle and an
overlapping window cannot both commit — the loser gets SQLSTATE `23P01`.
Phase 3 must catch that code and return `409 Conflict`.

The API contract is: **create the booking and its `BOOKED` availability row in
one transaction**; if the availability insert fails, the booking rolls back.

### 4.2 Time and amount checks

| Constraint | Rule |
| --- | --- |
| `vehicle_availability_time_order` | `endsAt > startsAt` |
| `bookings_time_order` | `returnAt > pickupAt` |
| `bookings_duration_positive` | `durationDays > 0` |
| `bookings_amounts_non_negative` | every amount column `>= 0` |
| `payments_amount_positive`, `refunds_amount_positive` | `amount > 0` |
| `reviews_rating_range` | `rating BETWEEN 1 AND 5` |
| `coupons_validity_order`, `coupons_value_positive` | `validTill > validFrom`, `value > 0` |

### 4.3 Partial unique indexes

```sql
CREATE UNIQUE INDEX "vehicle_images_one_primary_per_vehicle"
  ON "vehicle_images" ("vehicleId") WHERE "isPrimary" = true;

CREATE UNIQUE INDEX "addresses_one_default_per_user"
  ON "addresses" ("userId") WHERE "isDefault" = true;
```

A vehicle has at most one primary photo and a rider at most one default
address, without preventing any number of non-primary rows.

## 5. Data protection and payments

- **No card data.** `payments` stores only gateway identifiers
  (`providerOrderId`, `providerPaymentId`), method category, amount, status and
  failure metadata. Card number, expiry, CVV and card tokens are never
  modelled, collected or logged. Card entry happens inside the gateway's
  hosted UI; the API is redirected back with an opaque reference.
- **No secrets in the database.** Gateway keys, JWT secrets and SMTP
  credentials live in environment variables (`apps/api/.env`, never committed).
  `admin_settings` holds operational values such as support email and platform
  fee, not credentials.
- **PII.** `users`, `customer_profiles`, `driver_profiles` and `addresses` hold
  contact and identity data. Restrict reads to the owning user and support /
  admin roles, and use `audit_logs` for privileged mutations.
- **Password hashing.** Seed accounts use scrypt (`scrypt$<salt>$<hash>`) via
  the `node:crypto` implementation. Phase 3 replaces the seed helper with the
  auth module but keeps the same storage format.
- **Deletion.** Financial history uses `Restrict` so a user with bookings cannot
  be hard-deleted by accident; account closure should set `users.status =
  DELETED` and anonymise profile fields.

## 6. Migrations

The schema is managed by Prisma Migrate. The checked-in migration was generated
offline with:

```bash
npx prisma migrate diff \
  --from-empty \
  --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/20261109000100_init/migration.sql
```

The generated SQL was then extended with section 4's constraints. Phase 3 adds
three hand-written migrations:

| Migration | Contents |
| --- | --- |
| `20261109000200_auth_and_driver_assignment` | `OtpPurpose` enum, `refresh_tokens`, `verification_codes`, `bookings.driverId` + FK |
| `20261109000300_vehicle_from_price` | Denormalised `vehicles.fromPrice` and its index |
| `20261109000400_payment_method_optional` | Makes `payments.method` nullable while an order awaits checkout |

To change the schema:

```bash
npm run db:migrate --workspace=api -- --name describe_the_change
```

`prisma migrate dev` applies pending migrations, regenerates the client and
creates a new migration file. Review the SQL before committing; re-add any
hand-written constraint that Prisma dropped. For CI and production use
`npm run db:deploy --workspace=api` (no schema drift, no prompts).

`CREATE EXTENSION btree_gist` requires a database role allowed to create
extensions. The bundled `postgres:16-alpine` superuser and most managed
Postgres plans satisfy this; if not, run the extension step once as an admin
before deploying.

## 8. Operational queries

```sql
-- Is a vehicle free for a window?
SELECT NOT EXISTS (
  SELECT 1 FROM vehicle_availability
  WHERE "vehicleId" = $1
    AND status IN ('BLOCKED', 'BOOKED', 'MAINTENANCE')
    AND tsrange("startsAt", "endsAt", '[)') && tsrange($2, $3, '[)')
);

-- Booking with money totals
SELECT b.code, b.status, b."paymentStatus", b."totalAmount",
       COALESCE(SUM(p.amount) FILTER (WHERE p.status = 'PAID'), 0) AS paid
FROM bookings b LEFT JOIN payments p ON p."bookingId" = b.id
GROUP BY b.id;

-- Vehicle rating refresh (after publishing a review)
UPDATE vehicles v SET rating = s.avg, "reviewCount" = s.count
FROM (
  SELECT "vehicleId", ROUND(AVG(rating)::numeric, 2) AS avg, COUNT(*) AS count
  FROM reviews WHERE "isPublished" GROUP BY "vehicleId"
) s WHERE s."vehicleId" = v.id;
```
